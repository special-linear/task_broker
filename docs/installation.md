# Browser-led installation

Use one GitHub repository containing this complete source tree. Cloudflare clones it, installs the pinned lockfile, builds the browser, provisions D1, and deploys the Worker. The release archive is an alternative way to obtain the source; it is not itself a hosted application.

1. Create a Cloudflare account and a GitHub repository from the published project/template. Use the generated Deploy to Cloudflare link, or Cloudflare **Workers & Pages → Create → Import a repository**. Select the Free Workers plan.
2. Use `npm ci` for dependency installation, `npm run build` for the build command, and `npm run deploy` for the deploy command. The deploy command applies migrations through the **DB binding name**. Let the deployment flow provision a new D1 database named for this installation. For manual provisioning use **Storage & databases → D1 → Create database**, then bind it as `DB` and put its database ID in the configuration. Keep local, staging and production databases separate.
3. For a private deployment repository, edit `wrangler.jsonc` in GitHub's browser editor using `wrangler.example.jsonc` as the guide. For public source, keep that file generic and use ignored `wrangler.staging.local.jsonc` locally (or generate it from private deployment variables in CI before deploying). Set the Worker name, D1 ID, administrator origin, broker hostname, Access issuer/audience and owner emails. Configure custom domains for production; keep `workers_dev: false` and `preview_urls: false`. A staging-only shared workers.dev host is supported with distinct paths. Never enable local `DEV_AUTH` in a deployed configuration.
4. In Zero Trust, create a **Self-hosted Access application** for the administrator hostname's `/admin` and `/admin-api` paths, covering their descendants. Add an **Allow** policy with your exact owner email. Use a verified identity provider or One-time PIN. Avoid a hostname-wide policy when the broker shares that hostname. `/api/v1/*` must stay outside interactive Access. Save the Application Audience tag in `ACCESS_AUDIENCE`; the issuer is `https://YOUR-TEAM.cloudflareaccess.com`. If two applications are needed, provide their audience tags separated by commas.
5. In Worker **Settings → Variables and Secrets**, add `INSTANCE_EPOCH` as a fresh random UUID and `APP_SIGNING_SECRET` as at least 32 cryptographically random bytes encoded as hexadecimal. They must be different values. Cloudflare deployment credentials belong to the deployment system, never to the application or browser. Preserve the two application secrets on later builds.
6. Configure production custom domains in the Worker dashboard and keep them represented in the deployment configuration. Administrator and broker names must resolve to this Worker. The Worker independently checks host/path, Access JWT signature, issuer, audience, expiry, subject, and owner/administrator membership. A missing trust setting keeps the application closed.
7. Verify unauthenticated `/admin/`, nested assets, and `/admin-api/v1/me` require login. A bare compute request should return a JSON authentication error, with no Access login redirect. Alternate hostnames and root-level assets must not expose data. Only then sign in and choose **Initialize installation** on Start here.
8. Run the disposable demo, verify the Python result, download its CSV, and revoke/archive the temporary key and pool. Then create real work.

If an initial deployment cannot provision Access, complete step 4 in the dashboard. Do not substitute an application password, local development header, public setup token, or unprotected admin route.

Cloudflare documents [Deploy button resource provisioning and migrations](https://developers.cloudflare.com/workers/platform/deploy-buttons/). The Worker uses [Worker-first asset routing](https://developers.cloudflare.com/workers/static-assets/routing/worker-script/); these asset requests execute Worker code and count toward its traffic budget.

## Staging used during implementation

The public path/policy template is in `docs/staging-access.md`. Keep exact staging values in ignored `wrangler.staging.local.jsonc` and private operator notes. A maintainer runs `wrangler whoami` in their own environment, not assuming a Windows login is inherited. If login is required, use Wrangler's supported browser authorization flow. Authenticated API checks use a session established by `cloudflared access login --quiet <admin URL>`; the test tools never print the resulting token.

## Upgrades

Review the release notes and migration notes. Back up first. Update source files and the lockfile from the release, keeping your own deployment values, D1 identity, custom domains and secrets. Rebuild and apply the ordered additive migrations before deploying the new Worker. Test a disposable task. Ordinary upgrades must never generate a new epoch, recreate the database, or reset tasks. See [recovery](operations.md) for database restore, which is a different procedure.
